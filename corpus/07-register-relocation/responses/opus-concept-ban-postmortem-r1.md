Cleanup commits fail in production for a reason that has little to do with the code being removed and everything to do with how "unused" gets established. The tooling that flags dead code reasons over static references: it can see that no source file names a function, no template quotes a class. What it cannot see is anything that connects at runtime or across a boundary the analyzer never crosses. A CSS class applied by a string concatenated in JavaScript. A function reached only through reflection, a dependency-injection registry, or an event name matched by convention. A style rule that a third-party payment iframe or an A/B testing script targets from outside the repository entirely. Each of these looks orphaned from the compiler's vantage point and is anything but from the browser's.

Checkout is unusually exposed to this because it is the part of an application most likely to involve code paths nobody exercises casually. A branch that handles a declined card, a fallback for a specific gateway, a hidden field that only populates for certain regions — all of them appear cold in coverage data and unreferenced in a quick search, precisely because they run rarely. Removal tools measure frequency, and rarity reads as death. The CSS variant of this is nastier still, because deleting a rule usually produces no error at all: the button simply renders with zero height, or the overlay stops receiving pointer events, and everything continues to report success while no one can pay.

The second contributor is how these changes get reviewed. A diff that is entirely deletions invites a different reading posture than one that adds behavior. Reviewers skim, the description says "no functional change," and the size of the diff becomes evidence of harmlessness rather than a reason for scrutiny. Cleanup also tends to be batched, so a hundred small removals share one approval, and nothing in the process forces a per-item justification.

What catches this is mostly procedural. Require that any deletion cite the evidence for disuse — the search performed, the analyzer run, the production telemetry window — and treat dynamic string construction as disqualifying. Split cleanup from feature work so it can be reverted cleanly and bisected quickly. Route it through the same staged rollout and canary period as any behavioral change, since it is one. Prefer a deprecation window over immediate removal: annotate, log when the supposedly dead path executes, wait a full billing or seasonal cycle, then delete what stayed silent. Finally, gate revenue-critical flows behind end-to-end tests that actually complete a transaction, so a missing style rule fails a check rather than a customer.
