Cleanup commits fail because "dead" and "unused" are runtime claims disguised as static observations, and the codebase rarely gives you enough evidence to verify them. A function looks unreachable because nothing in the visible call graph invokes it — but reflection, dependency injection, cron jobs, feature flags, or a separate service calling through a public API can all reach code that a text search or even a decent static analyzer won't find. CSS is worse: a class selector with zero matches in the current templates can still be the target of JavaScript that adds it conditionally, an email-generation module rendered elsewhere, or a class computed dynamically from a string template that no grep will catch. The removal is safe in every code path the author checked and unsafe in the one they didn't.

Checkout flows are especially exposed to this because they tend to be old, high-traffic, and composed of code from several eras: a legacy discount calculator nobody touches, a CSS class that only activates during a specific promo or payment-method combination, a "deprecated" endpoint still hit by a mobile app version still in the wild. The very fact that this code is rarely modified — which made it look safe to remove — is often exactly why nobody remembered it was live.

There's also a scope problem specific to cleanup PRs: because the diff reads as subtractive and low-risk, it gets less scrutiny than a feature change of equivalent size. Reviewers skim for "does this look reasonable to delete" rather than tracing every removed symbol's actual callers, and CI often can't help because coverage gaps are precisely where dead-code assumptions are wrong — untested code is both the most likely to look unused and the least likely to have a test that fails when it's removed.

Review practices that catch this share one property: they replace assumption with verification. Concretely: require the PR to show *how* unreachability was confirmed — a repo-wide reference search including string-based and dynamic references, not just static call-graph tools; check application logs or APM traces for actual invocation of the code/routes/selectors over a meaningful window (a class or endpoint with zero hits in 30 days of production traffic is a much stronger signal than "I didn't see it referenced"); and treat cross-service or cross-repo usage as in scope — search client apps, mobile builds, and third-party integrations, not just the current repository. For CSS specifically, verify against rendered output across all page variants and A/B or promotional states, not just the default template. Staged rollout matters too: deploy cleanup changes behind a flag or to a canary slice first, and treat "big cleanup PR" as needing the same rollback plan and monitoring window as a feature launch, since the failure mode is a silent removal, not a visible bug.

Finally, org-level habits help: dead code should be marked deprecated and left inert for a release cycle before deletion, with logging added to prove it stayed unused, rather than deleted the moment it's spotted. That turns "I'm pretty sure this isn't used" into "I confirmed this wasn't used," which is the actual bar cleanup work needs to clear.
