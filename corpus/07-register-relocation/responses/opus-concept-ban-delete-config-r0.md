A module like this is unlikely to be as inert as it looks, and the first task is to be precise about what "unused" means. Static analysis of import statements catches only the most legible kind of dependency. Python offers many ways to reach a module without naming it in an import line: `importlib.import_module` on a string assembled at runtime, `__import__`, plugin registries that scan a package directory, entry points declared in `setup.py` or `pyproject.toml`, Django-style settings strings, Celery task routing, or a test conftest that pulls it in for fixtures. A grep for `legacy_flags` across every file type in the repository — including YAML, JSON, TOML, Dockerfiles, shell scripts, CI definitions, and infrastructure-as-code — is more informative than any import graph.

Then there is the question of side effects at import time. A flags module often does more than define constants. It may mutate `os.environ`, register signal handlers, set logging levels, monkeypatch a third-party library, populate a global registry that something else reads later, or seed default values that other code retrieves through a lookup helper rather than by direct reference. In those cases the module can be imported once, early, by something innocuous, and its absence would surface far from the deletion — as a changed default, a missing environment variable, or a behavior that only differs in production.

Beyond the codebase, consider consumers you do not control. Other repositories may import it if the package is published internally. Operations runbooks, alerting rules, or a data pipeline may reference flag names as strings. Old serialized state — pickles, database rows storing configuration keys, feature-flag records — may only be interpretable through this module. And some flags may be dead in the sense that nothing reads them today but alive in the sense that they encode a decision no one has re-derived, such as a workaround for a vendor API quirk.

For risk assessment I would work empirically rather than by reading alone. Add instrumentation: log or emit a metric whenever the module is imported or any attribute is accessed, deploy that to production, and let it run through a full business cycle including month-end and any seasonal jobs. Silence over that window is real evidence; silence from a code search is not. In parallel, read the git history and any linked tickets to recover intent, and check whether the module's 400 lines contain anything that a new implementation would have to reproduce.

If the telemetry stays quiet, delete it in a single reversible commit, behind a release you can roll back, and keep the removal separate from any other change so a regression points unambiguously at this one.
