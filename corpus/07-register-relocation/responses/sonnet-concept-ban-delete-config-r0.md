Removing an undocumented 400-line configuration module carries risk that is largely invisible to static analysis, because configuration code tends to be consumed indirectly rather than through explicit imports. The first category of risk is runtime string-based lookup: other parts of the system may reference flag names as strings — pulled from environment variables, database rows, feature-flag services, or dynamically constructed attribute lookups — meaning a simple "who imports this file" search will miss every caller. Second, serialized state can depend on it: if any of these flags were ever written into saved configs, database records, migration files, or cached objects, deserialization code may expect keys or defaults that only this module defines. Third, external interfaces may key off it silently — CLI argument parsers, admin panels, or API request handlers might branch on flag values without the module's name appearing anywhere near the branch. Fourth, test suites and CI scripts often import fixtures or constants from legacy modules specifically because nobody wanted to duplicate them, so deletion can break builds without breaking production. Fifth, and most insidious, disabled or "off" code paths may still reference these flags for their default values; removing the module could silently flip behavior rather than throwing an error, which is far more dangerous than a crash.

To assess the actual risk, start with static tooling: full-repository search (not just imports) for the module's filename, its individual flag names, and common access patterns like getattr or dictionary lookups against a settings dict it might populate. Follow with dynamic evidence: add logging or a deprecation warning inside the module in a non-production environment and observe whether it fires under a realistic workload, then extend that instrumentation to a canary or staging deployment over a period long enough to catch weekly and monthly batch jobs, not just daily traffic. Check version control history for the original context — commit messages and old pull requests often explain why a flag exists even after the reasoning has left institutional memory. Search infrastructure-as-code, environment files, and any external config store for references to the same flag names, since the dependency may live entirely outside the codebase. Finally, treat the removal as reversible rather than final: delete behind a feature flag or in a branch that sits in production alongside the original for one full deploy cycle, with alerting on any code path that still touches it, before deleting outright. If after all of that nothing fires, the risk is low, but "nobody understands it" is itself information — it means whoever could explain the edge cases is no longer available to answer questions when something breaks quietly weeks later.
