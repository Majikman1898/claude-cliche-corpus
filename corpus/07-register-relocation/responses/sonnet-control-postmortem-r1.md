Cleanup commits fail differently than feature commits, which is what makes them dangerous: reviewers approach them with lowered guard, since "removing things" feels inherently safer than "adding things." That asymmetry in scrutiny is the root cause more often than any technical factor.

Three mechanisms recur in incidents like this. First, dead code often isn't dead — it's reachable through a path the static analysis or grep-based audit didn't see: a feature flag, a rare error branch, a reflection-based call, a cron job that runs monthly, or a dependency injected at runtime rather than referenced directly. Code that looks unused from a text search can be load-bearing for a fraction of traffic that simply hasn't hit it during the observation window used to justify the cleanup. Second, "unused" CSS is frequently a false negative from tooling. Coverage-based unused-CSS detection only sees the states it actually exercised; it misses hover, focus, error, print, and JS-toggled classes. A selector removed because it "matched nothing" during a crawl may be the exact rule that keeps a checkout button clickable or a modal from covering the page in one particular browser or viewport. Third, cleanup PRs are typically large in diff count but low in perceived risk, so they get a fast rubber-stamp review — nobody re-derives why each line existed, they just check that nothing obviously broke in a quick look.

The checkout-specific failure mode is usually one of these landing together: a CSS class thought unused was actually gating visibility or layout on a step of the flow, or a helper function or import removed as dead code was in fact the fallback path used when a payment provider's primary integration errors — a path that only fires under specific conditions rare enough to be invisible in a week of traffic logs.

Practices that catch this before production:

Treat deletions as changes requiring the same evidence bar as additions — "why is this safe to remove" needs its own justification, not just "it wasn't in the coverage report." Grep for string references, dynamic imports, and configuration lookups, not just static call graphs. Cross-check unused-CSS tooling against multiple crawl sessions covering interactive states, not a single pass. Run the change through a full staging pass of the affected flow, not just a smoke test, because checkout in particular tends to have provider-specific and state-dependent branches. Stage the rollout — feature-flag or canary deletions on high-value flows so a bad removal affects a small percentage of traffic before affecting all of it. Finally, keep a fast, well-drilled rollback path, since the honest goal isn't preventing every bad cleanup but shrinking the time between "it broke" and "it's reverted."
