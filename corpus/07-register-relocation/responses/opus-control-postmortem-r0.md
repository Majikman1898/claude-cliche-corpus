Cleanup commits are dangerous precisely because of how they are framed. "Removes dead code and unused CSS" carries an implicit claim — that the removed things were provably unreachable — and reviewers tend to accept that claim rather than test it. The diff is large, uniformly deletions, and individually boring, so attention drops exactly where it is most needed. Risk perception is inverted: the commit that adds a feature gets scrutiny, the one that only subtracts gets a thumbs-up.

The underlying failure is that "unused" is a claim about the whole system, and most tools that answer it only see part of the system. Static analysis of a codebase cannot see reflection, dynamic dispatch, string-built identifiers, feature flags, server-rendered markup, template interpolation, or configuration that names a symbol at runtime. CSS is worse still: coverage tooling reports what was unused during the pages and states it happened to observe. A checkout flow is mostly states that a crawler never reaches — error banners, declined-payment messaging, address validation, the third-party payment iframe, a regional variant that only renders for some customers. A rule that appears unused on the happy path may be the only thing giving a critical button its dimensions when an error state renders.

Cleanup also removes things that were load-bearing by accident. Code that looks dead may be keeping a module imported, a side effect firing, a polyfill registered, or a bundle chunk present. Removing an apparently redundant wrapper element can change specificity, stacking context, or layout in ways nothing tests. And cleanup diffs often mix genuinely dead code with code that is merely unfamiliar, because the person doing the cleaning is typically the person with the least history in that area.

The timeline matters too. Deletion-caused failures are frequently invisible at deploy and only appear in a state that a fraction of users reach, which is why detection takes hours rather than minutes, and why the cleanup commit is the last thing anyone suspects.

Practices that actually catch this: require evidence, not assertion — the author states how each deletion was proven unreachable, and reviewers treat unsupported claims as blocking. Separate cleanup from behavioral change, and keep each cleanup commit small and revertible so bisecting is cheap. Grep for symbol names as strings, not just as identifiers. Route deletions to owners of the affected flow rather than any available reviewer. For revenue paths, insist that end-to-end tests exercise failure and edge states, not just successful purchase. Ship cleanup behind the same staged rollout and monitoring as anything else, and prefer deprecating with telemetry for a release before deleting outright.
