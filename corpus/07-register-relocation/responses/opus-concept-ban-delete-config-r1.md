A module like this rarely stays unused in the way a quick search suggests; it stays unreferenced by the specific patterns people know how to search for. The first category of silent dependency is dynamic access. If anything in the codebase reaches configuration through `getattr`, dictionary lookups on a flags registry, `importlib.import_module` with a name assembled from a string, or Django-style settings indirection, then grep for `legacy_flags` will come back clean while the module is being read on every request. Plugin systems, entry points declared in `setup.py`, and Celery task autodiscovery all resolve names at runtime rather than at import time.

The second category is import side effects. Four hundred lines is enough room for the module to be doing real work when it loads: registering signal handlers, mutating a shared settings object, monkeypatching a library, seeding defaults into a global dict, or setting environment variables that something else reads later. Under that pattern, the importer never touches a symbol from the module, so the dependency is invisible to static analysis, but deleting the file changes program behavior immediately. Check whether anything imports the module purely for its effect, including bare imports inside `__init__.py` files.

The third category lives outside the repository. Flags of this vintage are often read by operations tooling, migration scripts, cron jobs, Terraform templates, sibling services that import the package, notebooks used by analysts, or a deploy pipeline that sets an env var whose only consumer is this file. None of that shows up in a repo-wide search of application code.

To assess risk, I would combine several signals rather than trust any one. Run a search that covers string literals and flag names, not just the module path. Instrument before deleting: add a logging or metrics call at module import and at each flag accessor, ship it, and let it run through at least one full business cycle — a month if there is monthly batch processing, longer if there is quarterly reporting. Absence of hits over a real cycle is much stronger evidence than reading the code. Check version control for when each flag last changed and who touched it; check the issue tracker and any incident write-ups for mentions.

Then remove it in stages. Make the module raise or log loudly rather than deleting it outright, deploy behind whatever rollout mechanism exists, and keep the change trivially revertible. Delete the file only after a quiet observation period. The cost of that patience is small; the cost of discovering the dependency during a quarter-end batch run is not.
