Removing an undocumented 400-line configuration module is less risky in terms of what breaks immediately and more risky in terms of what breaks invisibly, weeks or months later, in a form nobody connects back to the deletion. The core danger with legacy flag modules is that their consumers are often indirect: other code doesn't call the module, it calls a wrapper, reads an environment-derived default, or imports a constant that happens to originate there. Static analysis (grep, import graphs, IDE "find usages") catches direct references but misses dynamic access — dictionary lookups by string key, `getattr` calls, config loaded through a plugin registry, or values re-exported under a different name in some `__init__.py`. It also misses anything reached only by a rarely-run code path: a holiday billing cycle, a disaster-recovery script, a monthly batch job, an admin-only feature flag toggle. A module can appear completely unused for the entire time anyone's watching and still be the only thing controlling behavior in a situation that hasn't occurred yet during the observation window.

There's also a distinction between "nothing imports this" and "nothing depends on this." Even if imports are clean, the module might set process-wide state as a side effect of being imported at all — registering a handler, mutating a global dict, setting an environment variable other code reads later. Deleting it silently changes that state rather than raising an error, which is worse than a crash because it fails quietly.

To assess this properly, I'd want several independent signals before trusting any one of them. First, exhaustive static reference search, including string-based and reflective lookups, not just import statements. Second, runtime evidence: instrument the module (log statements, or a lightweight tripwire that records every attribute access) and leave it running across a full business cycle — ideally a full year if seasonal logic is plausible — before concluding it's dormant. Third, version-control archaeology: read the commit history and any associated tickets to understand why it was introduced, since "nobody understands it" often means "the person who wrote it left" rather than "it does nothing." Fourth, check deployment and packaging configuration, not just source code — sometimes a file is referenced by a build script, a Docker layer, or a config-loading mechanism external to the Python import system.

Given all that, I'd treat deletion as a staged process rather than a single commit: first deprecate with loud warnings, then disable behind a flag with a fast rollback path, monitor a full cycle, and only then delete. That sequencing converts an irreversible guess into a reversible experiment, which matters most exactly when institutional knowledge about the code is gone.
