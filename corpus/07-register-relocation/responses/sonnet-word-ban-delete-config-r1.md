Legacy configuration modules like `config/legacy_flags.py` are risky to delete precisely because their dependencies are rarely expressed as visible imports alone. A 400-line flags file typically accumulates several categories of silent coupling. First, dynamic access: code elsewhere may reference flag names via `getattr`, string-keyed dictionary lookups, `globals()`, or reflection-based config loaders, none of which show up in a static import graph or a simple "who imports this" search. Second, side effects at import time: the module may register flags with a central registry, set environment variables, monkey-patch other modules, or run initialization code the moment it's imported, meaning downstream behavior depends on it having been loaded at all, independent of any specific symbol being used. Third, external and cross-boundary references: deployment scripts, CI pipelines, Terraform/Ansible configs, feature-flag dashboards, or other services might read values that originate from or mirror this module, especially if flag names are duplicated as environment variables or config keys elsewhere. Fourth, tests: a passing test suite doesn't prove non-use if the tests themselves mock out or stub the flags, or if coverage of the code paths gated by these flags is thin or absent. Fifth, conditional/dead-looking branches: flags controlling rare code paths (holiday sales logic, an emergency killswitch, a legacy data-migration fallback) may look unused simply because the triggering condition hasn't occurred recently, not because the path is truly dead.

A sound risk assessment would proceed in layers rather than trusting any single signal. Start with static analysis (grep across the full monorepo, not just the current package, including config files, YAML, and shell scripts, since flag names are often referenced as strings rather than imported symbols). Follow with dynamic verification: add deprecation warnings or logging inside the module and run it in production or staging for a full business cycle (including any cyclical/seasonal code paths) to catch runtime access that static analysis misses. Check version control history and commit messages for context on why the flags exist and whether they map to known incidents. Search issue trackers and internal docs for the module name. If available, use runtime coverage or telemetry tools to confirm which branches gated by these flags actually execute. Finally, treat deletion as reversible risk management rather than a one-shot decision: rename or quarantine the module first (e.g., move it behind a clearly marked deprecation shim that logs on access), keep it in a removable state for one or two release cycles, and only delete outright once the logging confirms zero touches across that window. This staged approach converts "nobody understands it" from a reason for anxiety into a solvable discovery problem, without requiring anyone to reconstruct tribal knowledge from memory before acting.
