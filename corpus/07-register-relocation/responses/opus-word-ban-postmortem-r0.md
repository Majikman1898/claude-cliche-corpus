Cleanup commits are dangerous precisely because of the assumption embedded in the word "cleanup." A change labeled as removal of dead code carries an implicit claim — that the code was dead — and that claim is usually established by a method far weaker than the confidence it produces. Static analysis, IDE "unused symbol" warnings, and grep across the repository all answer a narrow question: is this identifier referenced from other source in this repository? Production systems reach code by many other paths.

The common failure modes cluster into a few shapes. First, dynamic reference. Code invoked through reflection, string-keyed dispatch tables, dependency-injection containers, feature-flag lookups, templating engines, or serialized job payloads is invisible to the tools that declare it unreachable. A payment handler registered by name in a config file looks orphaned in the source graph. Second, cross-repository coupling. A function may have no callers in its own repo but be consumed by a separate service, a mobile client on an old release, a partner integration, or an analytics pipeline. Third, CSS in particular is notorious, because class names are frequently composed at runtime from data, injected by third-party widgets, or depended on by end-to-end test selectors and A/B testing tools. A checkout button that renders but is invisible, mispositioned, or zero-height is a total outage that no server error rate will reveal. Fourth, incidental behaviour: a removed import that was performing side-effectful registration, a deleted branch that was the only path setting a default, a stripped null check treated as redundant.

Compounding all of this is the sociology of review. Cleanup diffs are large, uniformly red, and individually trivial-looking, which invites skimming. They are typically approved quickly and by fewer people. They rarely get feature-flagged, staged rollouts, or explicit test plans, because there is nothing "new" to test. So the change with the least verification rigor is the one whose safety rests entirely on an unverified claim about reachability.

Practices that catch this: require the author to state, per deletion, the evidence that the code is unreachable, and treat "no references found" as insufficient for anything on a revenue path. Instrument before deleting — add logging or telemetry to suspected-dead code and let it run for a full business cycle, including monthly and quarterly jobs, before removal. Search beyond the repo boundary, including config, templates, and other services. Keep cleanup commits separate from functional changes and small enough to review honestly. For styling, rely on visual regression testing and real end-to-end tests through checkout rather than unit tests, since layout breakage is silent. Finally, ship cleanups through the same staged rollout and monitoring that features get, and ensure the checkout path has synthetic transactions that would have failed within minutes rather than hours.
