Caching layers exist independently of the database's internal cache because they solve a different problem, one the database's own cache is structurally unable to touch: the cost of asking the database anything at all.

The database's cache speeds up repeated reads within its own process — it keeps hot pages in memory so a query doesn't have to hit disk twice. But every request still has to reach the database. It still opens or reuses a connection, still gets parsed and planned as a query, still competes with every other query for lock manager attention and CPU time, and still crosses whatever network sits between the application and the database. None of that goes away just because the data happens to be sitting in memory on the other end. A caching layer in front of the database removes the trip entirely for a large fraction of requests — the application never asks the question in the first place.

That distinction matters most under load. The database's cache has a fixed capacity and shares it across every query pattern hitting that instance — reporting jobs, background writers, other services, all of it. It has no concept of which reads matter most to your application; it just evicts based on general-purpose heuristics. An application-level cache, by contrast, can be shaped around your actual access patterns: cache exactly the objects you fetch most often, in exactly the format your code wants to consume, for exactly as long as staleness is tolerable. That's a much narrower and more deliberate policy than a database cache can offer, because the database doesn't know anything about your application's read/write ratios or latency budget.

There's also a failure-mode argument. If the database gets slow — a bad query from another team, a failover, a spike in write volume — every request that depends on it gets slow too, cache or no cache, because the cache lives inside the same process that's struggling. A separate caching layer keeps serving already-cached responses even while the database is in trouble, which buys the application some insulation instead of failing in lockstep with it.

None of this means the layer is free. It introduces its own consistency questions — when to invalidate, how to handle a cache and database disagreeing after a write — and those are real complexities you're right to be suspicious of. But "redundant" implies the two caches are solving the same problem at the same layer, and they aren't. One optimizes disk access inside the database. The other decides whether the database gets asked at all. Removing the second doesn't just shift work back to the first — it removes a whole category of savings the first was never positioned to provide.
