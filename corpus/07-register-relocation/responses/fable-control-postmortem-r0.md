Cleanup commits fail for one structural reason: "dead" and "unused" are runtime properties, but they get assessed statically. A developer greps for references, finds none, and deletes — but many dependencies are invisible to text search. Code invoked via reflection, dynamic dispatch, string-built identifiers, dependency-injection containers, feature flags, or configuration files appears unreferenced while being load-bearing. CSS is especially treacherous: selectors are matched at runtime against markup that may be generated by templates, JavaScript, third-party widgets, A/B testing tools, or CMS content the auditing tool never rendered. A class that no template mentions literally can still be constructed by string concatenation or applied by a payment provider's embedded iframe wrapper. Checkout flows concentrate exactly these hazards — they integrate external scripts, conditional legacy paths (fallback payment methods, regional variants), and states that only occur with real money in play, so they are simultaneously the most dynamic part of the app and the least exercised in local testing.

Compounding this, cleanup changes get lighter review precisely because they claim to change nothing. A deletion-only diff looks safe; reviewers skim it. Test suites rarely help, because code that was believed dead usually has no tests — the absence of test coverage was part of why it looked removable. And staging environments often lack the conditions (production feature-flag states, real payment gateway responses, long-tail browsers, cached HTML referencing the deleted CSS) that make the code live.

Review practices that catch this class of failure:

- **Treat deletions as behavior changes.** Require the author to state *how* deadness was established — static grep is a hypothesis, not proof. Ask "what evidence shows this never executes in production?"
- **Runtime verification before removal.** Instrument suspected-dead code with logging or counters and let it soak in production for weeks (covering monthly billing cycles, regional traffic, flag states) before deleting. For CSS, use coverage tooling against real production sessions, not a rendered sample.
- **Tombstoning / two-phase removal.** First ship a change that disables or logs; delete only after the tombstone stays silent. This converts a mystery outage into a metric.
- **Scope-aware review routing.** Any diff touching checkout, auth, or payment paths gets domain-owner review regardless of how mechanical it looks.
- **Small, separable commits** so a bad deletion reverts in minutes, plus synthetic end-to-end checkout monitoring that alarms on conversion drop — the three-hour outage usually means detection, not the fix, was slow.

The meta-lesson: risk correlates with what code touches, not with how boring the diff looks.
