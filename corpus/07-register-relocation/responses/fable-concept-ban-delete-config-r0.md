A module can be "unused" by every static measure and still be exercised constantly, because Python offers many ways to reach code that grep and import analyzers miss. The first category is dynamic access: `importlib.import_module("config.legacy_flags")`, `__import__` with a string built at runtime, `getattr(config, name)` where the name comes from a database row, an environment variable, or a YAML file. Feature-flag systems are especially prone to this — the whole point of such a module is often to be consulted indirectly. Second, import-time side effects: even if nothing calls its functions, merely importing the module may register defaults, mutate a shared settings object, set environment variables, or populate a registry that other code reads later. If a package `__init__.py` imports it, deleting it changes behavior everywhere without any direct reference. Third, out-of-repo consumers: cron jobs, deployment scripts, Ansible playbooks, ops runbooks, sibling services that pip-install this repo, and one-off admin scripts on production hosts. Fourth, serialized state — pickles, Celery task payloads, Django migrations — can embed the module path and fail to deserialize after removal. Fifth, tests and tooling may patch or import it in ways that mask real usage patterns rather than reveal them.

Assessment starts with cheap searches done properly: grep the whole organization, not just this repo, for the module name and for each flag name individually, since string-keyed lookups reference symbols, not the file. Check `__init__.py` chains for transitive imports. Read the module itself for side effects at import time and for anything that writes to shared state. Then move to runtime evidence: add logging or a deprecation warning to the module's import and to each public function, deploy that, and watch production telemetry for a full business cycle — a quarter, ideally, because some code runs only at month-end close, year-end reporting, or during rare failure-recovery paths. Zero hits over one week proves little; zero hits over ninety days across all environments is meaningful. Check version-control history for who last touched it and why, and ask them if they're reachable.

The actual removal should be staged rather than atomic. First replace the module with a stub that logs and raises a descriptive error naming a ticket, so any surviving caller fails loudly and traceably instead of silently reading a missing flag as false. Ship that, wait through another full cycle, then delete the stub. Keep the change in its own commit for a clean revert, and document in the commit message exactly what evidence of non-use was gathered, so the next team inherits the reasoning rather than another mystery.
