Static import analysis is the obvious first step, but it's also the least reliable signal for a module like this, because configuration code is precisely the kind of thing that gets loaded through non-obvious channels. The dependencies most likely to be invisible to grep are: dynamic imports (`importlib.import_module`, `__import__` with a string built at runtime, plugin registries that discover modules by naming convention); string references in configuration itself — settings files, environment variables, Django-style `INSTALLED_APPS` or `SETTINGS_MODULE` strings, entry points in `setup.py`/`pyproject.toml`, Celery task paths, YAML/JSON deployment manifests; and import-time side effects. That last one is the sneakiest: a 400-line "flags" module may register defaults, mutate a global registry, monkeypatch something, or seed a feature-flag cache merely by being imported once from an `__init__.py`. In that case nothing references its names, yet removing it changes behavior.

Dependencies can also live entirely outside the repo: sibling services or internal tools that import the package, ops scripts on cron boxes, notebooks, CI jobs, and serialized data — pickles and some ORM/migration artifacts embed dotted module paths, so unpickling old objects or replaying old jobs can fail months later. "Nobody on the team understands it" is itself a risk signal: institutional knowledge of who consumes it left with the module's authors.

To assess risk I'd layer several imperfect signals rather than trust any one. First, repo-wide and org-wide code search for the module name and for each public symbol it defines, as strings as well as imports. Second, check packaging metadata and framework config for string-path references. Third, and most decisive: instrument rather than speculate. Add an import-time log line or deprecation warning to the module, deploy it, and let it run through a full business cycle — including month-end jobs, deploys, incident tooling, and any quarterly batch processes, since rare code paths are where legacy config hides. Zero import events over a representative window is strong evidence; a week of silence is not.

For the removal itself, make it cheap to reverse. Delete in a dedicated commit with nothing else in it, behind a normal deploy (not bundled with a migration), ideally replacing the module first with a stub that raises a loud, descriptive error on import so any surviving consumer fails fast with an actionable message instead of a bare `ModuleNotFoundError`. Keep the stub for a release or two, watch error tracking, then remove it. If any flag values in the module feed persisted state, snapshot their effective values first, since the flags' *values* — not the code — may be the real dependency.
