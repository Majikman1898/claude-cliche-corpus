Silent dependencies on a module like `config/legacy_flags.py` fall into categories that static reasoning about imports will not surface. The most common is dynamic access: `importlib.import_module`, `__import__`, `getattr` on a settings object, or a string-keyed registry that resolves flag names at runtime. A grep for `legacy_flags` catches literal imports but misses `import_module(f"config.{name}")`. Equally common is import-for-side-effect — the module may register signal handlers, populate a global registry, monkeypatch a third-party default, set environment variables, or seed a singleton at import time. If any other module imports it purely for those effects, the import statement looks vestigial and the deletion looks safe right up until a default silently changes in production.

Second, configuration modules tend to be read by things that are not Python. Deployment templates, Ansible or Terraform files, Docker entrypoints, CI jobs, and ops runbooks may reference flag names as strings. Serialized state is worse: if flag values were ever pickled, cached, or written into database rows, feature-flag tables, or user preference blobs, removal changes deserialization behavior rather than raising an error. Frameworks add their own path — Django settings modules, pytest conftest chains, plugin entry points declared in `setup.py`/`pyproject.toml`, and Celery task registries all load modules by name from configuration rather than by import.

Third, the module may be doing nothing visible but supplying fallbacks. Four hundred lines of defaults matter only when the primary configuration source is absent — which is precisely the rare path: disaster recovery, a fresh environment, a degraded upstream, a batch job that runs quarterly. Absence of traffic through the code is weak evidence when the code exists to handle absence.

Risk assessment therefore should combine several independent signals rather than trusting any one. Search the whole organization, not the repo: every service, infra repo, notebook, and scheduled job, for the module path and for individual flag names as bare strings. Read the module's git history and blame to recover intent — the commit that added each flag usually names the incident it was for. Instrument before deleting: add import-time and attribute-access logging (a module `__getattr__` works well), ship it, and let it run through at least one full business cycle including month-end and any quarterly jobs. Check whether the module has meaningful test coverage, since untested code is both likelier to be dead and likelier to break unnoticed.

Then prefer a reversible sequence: deprecate with warnings, then raise on access, then delete — each step behind a release that can be rolled back cheaply. The cost of a staged removal is a few weeks; the cost of a silent default change discovered during an incident is much higher.
