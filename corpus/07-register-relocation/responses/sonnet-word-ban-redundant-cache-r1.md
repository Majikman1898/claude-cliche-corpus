Caching between the application and the database exists for a reason that has nothing to do with whether the database "already caches" — it's about what kind of work you're saving, and where.

A database's internal cache (buffer pool, query plan cache, page cache) is optimized for one thing: avoiding disk I/O for data the engine already has in memory. That's valuable, but it still costs you a network round trip, connection overhead, query parsing, lock acquisition, and often a nontrivial join or aggregation, even when every row involved is sitting in RAM on the database server. An in-memory application-layer cache skips all of that. The difference between a Redis GET at sub-millisecond latency and a "cached" database query that still has to traverse the network stack, re-parse SQL, and re-execute a query plan is often an order of magnitude, sometimes two. At low traffic that gap doesn't matter. At the throughput this service actually handles, it's the difference between the database staying comfortably under load and the database becoming the bottleneck for everything that shares it.

That last point is the real reason removal is dangerous, not just slow. The database is a shared, finite resource — every other service, every batch job, every report query is drawing from the same connection pool and the same I/O capacity. When you remove the caching layer, you're not just making this one code path slower; you're routing a large volume of repeated, predictable reads directly onto infrastructure other teams depend on. We've seen this pattern before: a "harmless" cache removal during a refactor looked fine in staging, then took down checkout during a traffic spike three weeks later because the connection pool saturated and queries that used to take 2ms started queueing behind ones taking 200ms. The cache wasn't decorative — it was absorbing a class of failure that only shows up under load, which is exactly the condition under which you can least afford to discover it.

There's also a correctness dimension: the cache here isn't just re-serving DB rows, it's holding computed or aggregated results that would otherwise require re-running expensive joins on every request. Removing it doesn't just add latency, it adds CPU cost to the database that scales with request volume, not with data size.

None of this means the cache is beyond question — cache invalidation bugs, stale-data risk, and added operational complexity are real costs worth weighing. But "the database already caches" isn't a valid reason to remove it, because the two caches solve different problems at different layers. If you want to evaluate removing it, the right approach is to load-test the change against production-like traffic and measure database saturation, not to reason about it from first principles.
