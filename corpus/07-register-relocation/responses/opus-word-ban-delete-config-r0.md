A module like this is dangerous to remove precisely because the evidence of its use tends not to live in the import graph. Static analysis will tell you nothing imports `config/legacy_flags.py`, and that finding is close to worthless on its own. Python offers many ways to reach a module without a literal import statement: `importlib.import_module` on a name assembled from a string, `__import__` in a plugin loader, entry points declared in `setup.py` or `pyproject.toml`, Django-style settings strings, Celery task routes, or a dotted path sitting in a YAML file that some factory resolves at runtime. A grep for the module name is therefore more informative than a grep for the import, and a grep for the individual flag names is more informative still, because callers frequently copy the string key rather than the symbol.

The second class of dependency is side effects at import time. Legacy flag modules often do work when loaded — registering defaults into a global registry, monkeypatching a library, seeding environment variables, mutating a singleton config object. In that pattern the module can appear unreferenced everywhere except one `import` near the top of an `__init__.py`, and deleting it changes the behavior of code that never mentions it. Reading the module top to bottom for anything executing outside a function body is a cheap, high-yield check.

Third, consumers may be outside the repository entirely. Ops runbooks, Terraform templates, CI jobs, cron scripts, a sibling service that reads the same flag names from a shared store, or a data pipeline that pins an old release — none of these show up in a code search of this project.

For assessing risk, I would sequence the cheap and reversible checks first. Search the full organization, not just the repo, for the module path and for each flag name. Check version control history: who touched it last, why, and whether any commit message explains what it guards. Check whether the flags are read anywhere in production configuration or feature-flag tooling. Then instrument rather than delete — add logging or a deprecation warning on module import and on each flag read, ship it, and let it run through at least one full business cycle, including month-end and any seasonal batch jobs, since infrequent paths are exactly the ones nobody remembers. Silence over that window is real evidence; silence from a static scan is not.

If the observation period is clean, remove it in a single revertible commit behind a fast rollback, and keep the deletion separate from other changes so the blame is unambiguous. The main failure mode is confusing "we cannot find a caller" with "there is no caller."
