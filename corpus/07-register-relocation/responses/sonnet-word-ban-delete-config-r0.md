Legacy configuration modules like this are dangerous precisely because "unused" is hard to prove and easy to disprove after the fact. Config code differs from ordinary logic in that its call sites are often indirect: values get read via string-keyed lookups, environment variable fallbacks, dynamic imports, or reflection-style getattr calls that a static grep or IDE "find references" won't catch. A flag defined in legacy_flags.py might be imported once under an alias three layers removed from anywhere the word "legacy_flags" appears, or read by name from a settings dictionary assembled at runtime.

Several categories of hidden dependency are worth checking specifically. First, deployment and infrastructure: CI/CD pipelines, Docker entrypoints, or Kubernetes configmaps may set environment variables or mount files that only this module parses. Second, feature flags controlling rarely-exercised code paths — a flag gating a quarterly batch job, a disaster-recovery mode, or an admin-only feature won't show activity in normal test runs or production traffic sampling, but removing it could break that path silently until the day it's needed. Third, external or cross-team consumers: another service, a scheduled job, or a data pipeline maintained by a different team might import this module even though nobody on the current team wrote or reviewed that dependency. Fourth, backward-compatibility shims — code that translates an old config format to a new one for systems that haven't migrated.

To assess risk before deletion, I'd combine several evidence sources rather than trust any single one. Static analysis (grep/AST search across the entire monorepo, not just the current service) for both the module name and any flag names it defines, including as strings. Runtime evidence: code coverage or logging instrumentation added for a full deploy cycle (ideally spanning a release, a batch/cron cycle, and a peak-load period) to see if any line actually executes. Git blame and commit history to find the last meaningful change and whether it correlates with an incident. Search of build artifacts, generated documentation, and any service registry for consumers outside the current repo. And a deprecation warning added first — log a warning wherever the module is touched, ship it for a full cycle, and see if anything fires.

Given all that, I'd recommend a staged removal rather than a single deletion commit: first add loud runtime warnings when it's exercised, then after a clean observation window (long enough to span monthly/quarterly jobs), replace the module body with an error stub for one release rather than deleting the file outright, so any remaining dependency fails fast and visibly instead of silently. Only delete the file once that stub has gone through a full deploy cycle without triggering.
