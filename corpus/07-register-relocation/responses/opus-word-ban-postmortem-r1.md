Cleanup commits are dangerous precisely because they are framed as risk-free. The mental model behind them is that the code being removed does nothing, so removing it can change nothing. That reasoning is only valid if the person doing the removal has complete visibility into every consumer of the code, and in a system of any age, they almost never do.

The most common failure is a gap between what static analysis can see and what actually runs. Code reached by reflection, dynamic dispatch, string-keyed lookups, feature-flag branches, dependency injection, or serialization frameworks has no visible caller. A linter reports it as unreachable. Production reaches it constantly. The same applies to CSS: a class may be absent from every template in the repository because it is composed at runtime, injected by a third-party widget, or emitted by a content management system that nobody greps. Selectors also do work beyond appearance — they can gate visibility, stacking order, or hit targets, so deleting a rule that "styles nothing" can leave a submit button rendered under an overlay, technically present and entirely unclickable.

The second failure mode is that dead code is often not dead but dormant. It serves an error path, a retry branch, a legacy client version, a regional variant, a fallback for a degraded dependency. Under normal conditions it never executes, which is exactly why it looks removable and exactly why the outage arrives hours or days later, when the rare condition fires and the handler is gone.

Detection is the third problem. Cleanup changes usually pass tests, because tests exercise the paths that matter to developers, not the ones that survive by accident. They also skip the scrutiny a feature change receives. A large diff of pure deletions invites approval by volume rather than by line, and reviewers read the diff rather than searching for what the deleted names touch.

Practices that catch this are mostly about refusing the framing. Cleanup should be reviewed as a behavioral change, not a cosmetic one, with the same rollout discipline: separate commits from feature work, deploy behind a flag or in isolation so attribution is immediate, and keep them out of large batched releases. Reviewers should require evidence of non-use rather than absence of use — runtime telemetry, log instrumentation left in place for a full business cycle, or a deprecation period where the code warns before it disappears. Delete in stages: instrument, observe, then remove. Prefer removing in small, individually revertible units. Finally, treat critical revenue paths as requiring synthetic monitoring that runs continuously, so a broken checkout surfaces in minutes rather than through customer complaints three hours in.
