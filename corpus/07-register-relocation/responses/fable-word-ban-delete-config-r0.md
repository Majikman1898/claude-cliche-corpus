Silent dependencies on a module like this fall into several categories, roughly ordered by how hard they are to find. The easiest are static imports, which grep and IDE tooling catch. Harder are dynamic references: `importlib.import_module` or `__import__` calls built from strings, plugin registries, Django-style `INSTALLED_APPS` or settings strings, and entry points declared in setup.cfg or pyproject.toml. A module named `legacy_flags` is especially likely to be consumed by name via configuration rather than code — feature-flag frameworks often resolve flag providers from environment variables or YAML, so the referencing string may live outside the repository entirely.

Next come import side effects. A 400-line config module almost certainly executes code at import time: registering defaults, mutating a global settings object, patching another module, or seeding environment variables. Even if nothing reads its symbols, something may depend on it having been imported — often transitively through a package `__init__.py`. Deleting it can change behavior without producing an ImportError anywhere, which is the most dangerous failure mode because tests pass and defaults silently shift.

Beyond the codebase itself, consider external consumers: other repositories that pip-install this package, ops scripts, cron jobs, CI pipelines, notebooks, and serialized artifacts. Pickled objects encode module paths, so unpickling old data can fail months later. Log parsers or dashboards may key on strings the module emits. And the flags themselves may be dormant rather than dead — code paths exercised only during incidents, year-end processing, or for one legacy customer.

Assessment approach, cheapest first. Trace history: `git log` for last meaningful change, and search commit messages and issue trackers for the flag names. Search broadly — organization-wide code search for the module path and for each individual flag string, not just the import. Then instrument rather than guess: add a deprecation warning or a logging statement at module import and at flag access, deploy it, and let it soak in production for a full business cycle (long enough to cover monthly and quarterly jobs — a week is not enough for a config module). Zero hits over that window is real evidence; static analysis alone is not.

For removal, prefer a staged retreat over deletion: first replace the module with a stub that raises a loud, descriptive error on import or attribute access, ship that, and watch. If nothing breaks after a release cycle, delete the stub. This converts an unknown risk into an observable one, keeps the failure message actionable for whoever hits it, and makes rollback a one-line revert instead of an archaeology project.
