Cleanup commits fail catastrophically for a specific reason: "dead" and "unused" are judgments about the code as read, not as executed, and the two frequently diverge. Static analysis and grep-based audits see what's referenced in source; they don't see what's referenced by build tooling, feature flags, A/B test cohorts, error-path fallbacks, or conditionally-loaded bundles that only activate under specific runtime conditions. A CSS class with no visible reference in the current codebase may be injected by a third-party script, targeted by a browser extension users rely on, or referenced by a class name constructed via string concatenation that no linter can trace. Code that looks unreachable in the primary flow may be the fallback path for a payment provider timeout that only fires under real-world network conditions rarely seen in staging.

The checkout-flow failure mode specifically tends to involve a few recurring patterns. First, the removed code was reachable via a code path exercised only by a subset of traffic — a particular browser, a particular payment method, a legacy client version still in use, or a redirect-based flow rather than the primary happy path. Second, styling that appeared cosmetic was actually functional — CSS controlling form field visibility, error message display, or JavaScript hooks keyed to class names. Third, the change passed CI because tests exercise the common path, and the deleted logic served an edge case that tests don't cover, either because it predates the test suite or because writing a test for it seemed disproportionate to its apparent importance.

The review practices that catch this share a common thread: they substitute evidence for confidence about what "unused" means. Runtime usage analysis — checking access logs, error tracking, or code-coverage instrumentation in production over a meaningful window, not just staging — is more reliable than static reference-counting, because it captures what actually executes rather than what's textually linked. Grepping for dynamic references (string-built selectors, reflection, template interpolation) before deletion catches cases where static analysis structurally can't see the dependency. Deploying cleanup independently of feature work, in small increments, makes it possible to attribute a regression quickly rather than debugging it inside a larger changeset. Staged rollout with real traffic, rather than an all-at-once deploy, would have surfaced the checkout failure against a fraction of users within minutes instead of hours. And treating any change that touches checkout, auth, or payment surfaces as requiring elevated review — regardless of how trivial the diff looks — closes the gap that "harmless cleanup" language tends to open: the description of a change as low-risk becomes an assumption nobody re-verifies, and the size of a diff gets treated as a proxy for its blast radius when the two are frequently uncorrelated. The fix isn't more caution in general; it's making the review process ask "how do we know this is unused" as an explicit, answerable question rather than an implicit one.
