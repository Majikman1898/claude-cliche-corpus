Cleanup commits carry a specific and underappreciated risk: they are defined by what they remove, and removal is the one class of change whose failure modes are invisible in the diff itself. When you add a function, the reviewer can read it and reason about whether it is correct. When you delete one, correctness depends entirely on facts that are not on the screen — who else called it, what referenced that CSS class, what the runtime does when the selector no longer matches. The diff shows the deletion; the risk lives in the codebase's shape around it.

The usual mechanism is a gap between static reachability and actual reachability. Code looks dead because no static reference exists, but it is reached through something the analyzer cannot follow: a string-based dispatch table, reflection, a dynamic import, a feature flag evaluated at runtime, a webhook or cron entry that names a handler in configuration rather than in code, a template rendered by a different service. Checkout flows are unusually rich in exactly these patterns — payment provider callbacks, third-party scripts keyed to DOM hooks, A/B test branches, error and retry paths that only execute on the unhappy path.

Unused CSS is the same problem in a different dialect. A class can be absent from every template you can grep and still be applied at runtime by JavaScript, by a CMS field, by an email template, or by a vendor widget. And CSS failures are quietly severe: a removed rule does not throw. The page renders, the button is simply invisible, or overlapped, or the overlay that traps clicks never gets its z-index. No error surfaces, no exception is logged, so alerting sees a healthy service while conversion silently goes to zero. The three-hour duration is the real tell here — not that something broke, but that nothing screamed.

Cleanup also arrives socially disarmed. It is labeled harmless, it touches many files shallowly, and reviewers pattern-match on the label rather than the content. A thousand-line deletion gets less scrutiny than a fifty-line feature, precisely inverted from the risk.

Practices that catch this: treat deletions as behavioral changes and hold them to the same testing bar as features. Keep cleanup commits separate from functional ones and small enough to bisect. Require the author to state, per removal, the evidence it is dead — not "grep found nothing" but runtime evidence: telemetry showing zero hits over a meaningful window, coverage data, logs from a deprecation shim left in place for a release cycle. Prefer a two-step retirement — instrument, wait, then delete. Run visual regression and end-to-end tests through the actual revenue path, since those are the only checks that detect a missing style rule. Ship behind a flag or canary so blast radius is bounded. And add synthetic monitoring of the funnel itself, so a silent visual break registers as an incident rather than a slow bleed someone notices hours later.
