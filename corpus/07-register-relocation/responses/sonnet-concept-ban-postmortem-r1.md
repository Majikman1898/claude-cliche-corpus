Cleanup commits fail not because the code they remove is wrong, but because "unused" is a claim about the present, and the present is smaller than the system. A function looks dead if you search the codebase and find no callers, but that search rarely covers everything that actually invokes code in production: feature flags gating a rarely-hit branch, a cron job that runs monthly, a webhook from a third party, a mobile client still on an old version calling an old endpoint, an admin tool nobody documented. The same applies to CSS: a class with no matches in the templates you searched can still be applied by JavaScript that builds class names dynamically, by a string concatenation, by an email template rendered elsewhere, or by a third-party widget injecting markup that expects your styles. Static analysis tools are good at finding references within their own scope and blind to everything outside it.

Checkout flows in particular tend to be exactly the kind of code that looks unused by ordinary reading. They're often reached through conditional paths — a specific payment method, a specific currency, a retry after a failed charge, a fallback for browsers without some capability. A path that fires for five percent of transactions can look, in a quick grep, indistinguishable from a path that fires for zero. The commit author sees no obvious callers and reasonably concludes the code is safe to remove; the five percent shows up only when real traffic arrives.

Three review practices catch this reliably, and none of them are exotic. First, treat deletions with the same scrutiny as additions rather than less — a diff that only removes lines often gets skimmed on the assumption that removal can't introduce new behavior, which is precisely the false assumption that causes these outages. Second, verify "unused" empirically rather than by inspection: instrument the code path with logging or metrics for a full business cycle (not just a day, since some paths only fire weekly or at billing time) and confirm zero invocations before deleting, rather than trusting a text search. Third, stage the removal — deploy behind a flag, or merge but don't release, or delete in a way that fails loud rather than silent, so if something does still depend on the removed code, it surfaces as an immediate, obvious error rather than a slow, confusing symptom discovered by customers.

The deeper practice is cultural: treat "this looks unused" as a hypothesis to test, not a conclusion to act on, especially in revenue-critical paths where the cost of being wrong is measured in hours of downtime rather than a quick revert. Cleanup commits get less scrutiny precisely because they're framed as harmless, which is exactly why they deserve the same pre-deploy validation as any other production change touching checkout.
