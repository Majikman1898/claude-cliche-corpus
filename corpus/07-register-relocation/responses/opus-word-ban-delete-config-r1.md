A module that "appears to be unused" is usually judged by static evidence — nobody imports it, grep finds no callers — and static evidence is precisely what a configuration module is best at evading. The first category of hidden dependency is dynamic resolution: `importlib.import_module`, `__import__`, entry points declared in `setup.py` or `pyproject.toml`, plugin registries that scan a package directory, Django-style settings strings, Celery task autodiscovery, or a name assembled from an environment variable. None of these leave a grep-visible reference. A flag module is a natural target for exactly this pattern, because the whole point of feature flags is late binding.

The second category is import side effects. Configuration modules frequently do work at import time — register defaults into a global dict, monkeypatch a library, set warning filters, mutate `os.environ`, seed a singleton, or populate a registry that other modules later read by key rather than by symbol. If some other module imports `legacy_flags` purely for effect, a linter will flag that import as unused and a well-meaning cleanup will delete it, breaking things long before you delete the file. Conversely, the module may be imported transitively through a package `__init__.py`, so removing it changes what a seemingly unrelated import brings into scope.

Third, the consumers may not be Python at all. Ops scripts, cron jobs, Ansible or Terraform templates, Dockerfile entrypoints, CI configuration, notebooks, and one-off migration scripts often reference config paths by string. Serialized state is another trap: pickles, cached objects, or database rows storing fully-qualified class paths will fail to resolve after the module disappears, and that failure surfaces at deserialization time in production, not at import time in CI.

For risk assessment, I would work in layers. Start with a repository-wide plain-text search for the module name, the flag names it defines, and any string constants it exports — across all file types, not just `.py`. Check the packaging metadata for entry points. Read the module itself for import-time side effects and for anything that writes to a shared namespace. Then get runtime evidence: add import-time logging or a `sys.modules` audit hook in production for a full business cycle — long enough to cover monthly and quarterly jobs, which are the classic thing a two-week observation window misses. Check version control history for why it was added and whether the original author left a rationale in commit messages or tickets.

Finally, prefer reversible steps. Deprecate before deleting: raise a warning on import, then a hard error, then remove. Delete behind a revertable commit, and keep the module's content recoverable in history rather than trusting that anyone will remember what it did.
