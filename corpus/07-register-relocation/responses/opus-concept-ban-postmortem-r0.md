Cleanup commits fail in production for a simple reason: the criteria that make code look dead are almost never the criteria that make it actually dead. A reviewer scanning for unused symbols relies on static reachability — nothing references this function, no selector matches this class, this branch is unreachable from the entry points I searched. Production disagrees, because real systems reach code through paths that static analysis cannot see. Reflection, dynamic dispatch, string-keyed lookups, feature flags evaluated at runtime, template interpolation, and event handlers bound by name all invoke code without a literal reference to it. Unused CSS is worse still: class names are frequently assembled at runtime from data, injected by third-party widgets, or applied by scripts the stylesheet's author never read.

Checkout flows concentrate exactly the conditions that make this dangerous. They are the most heavily patched part of most codebases, so they accumulate compensating logic — a defensive null check added after an incident, a hidden field a payment processor reads, a CSS rule that exists solely to keep an element off-screen rather than absent from the DOM. That history is invisible in the diff. A rule like `.legacy-hidden { display: none }` looks like debris; deleting it makes a debug element visible over the submit button, or exposes a form field that then gets posted. Similarly, a function with no callers in the repository may be called by a webhook, a scheduled job, another service, or an older mobile client still in the field.

Compounding this, cleanup changes get systematically less scrutiny than feature changes. Reviewers skim deletions. Test suites rarely fail, because tests exercise the same reachable paths the reviewer already checked — the untested runtime path is precisely the one that breaks. And because the change is nominally a no-op, teams often skip staged rollout, so the blast radius is immediate and total.

The practices that catch this are mostly about replacing inference with evidence. Require deletion PRs to cite proof of disuse: production telemetry showing zero invocations over a meaningful window covering monthly and seasonal traffic, not a grep result. Instrument before deleting — log the suspect path, ship, wait, then remove. Separate cleanup from functional changes so rollback is clean and attribution is unambiguous. Route deletions touching revenue paths to owners who know the history. Treat CSS as dynamically referenced by default and verify visually across real checkout states, including error and edge-case renders. Finally, ship cleanups behind the same progressive rollout and monitoring as features, and define what a checkout regression looks like in your dashboards before you need to spot one.
