That's a good question to ask, and the answer comes down to what each cache actually saves you.

The database's internal cache — its buffer pool or page cache — saves disk I/O. When a query hits cached pages, the database skips reading from storage. But that's the only cost it eliminates. Every request that reaches the database still pays for everything else: the network round trip from the application to the database, connection acquisition from the pool, query parsing and planning, executing the plan (joins, sorts, aggregations still run even when every underlying page is in memory), and serializing results back over the wire. For the queries our caching layer covers, executing against fully-cached pages might take a few milliseconds; returning the same result from the application cache takes microseconds locally, or well under a millisecond from something like Redis, and skips query execution entirely. The database cache stores raw pages; ours stores finished answers.

The second issue is where the work lands. The database is our hardest component to scale — it's stateful, and adding capacity means replicas, failover complexity, and consistency questions. The cache layer absorbs the bulk of read traffic before it ever reaches the database, and it scales horizontally by just adding nodes. If we removed it, every cached read would become a real query. The database might handle that on an average Tuesday; the question is what happens at peak, or when a hot key gets hammered — a popular item, a viral page — turning into thousands of identical queries per second against the same rows. The cache collapses that into one query and thousands of memory lookups. Without it, our load-spike story becomes "hope the database keeps up," and databases fail much less gracefully than caches do.

Third, the cache often stores things the database never computed in that shape: assembled objects built from several queries, rendered fragments, results of expensive aggregations. The buffer pool can't help there at all — it caches inputs, not outputs.

None of this means the layer is free. Invalidation logic is genuinely tricky, stale reads are a real failure mode, and it's fair to audit whether every cached path still earns its complexity — some individual cache usages may indeed be vestigial. But "the database has its own cache" isn't the argument for removing them, because the two caches solve different problems: the buffer pool makes queries cheaper, while the application cache makes queries unnecessary. A useful exercise: check the cache hit rate and estimate what that traffic looks like as raw QPS against the database. That number usually ends the conversation.
